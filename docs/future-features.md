# Future Features — voice-acp

> רעיונות שעלו במהלך התכנון אבל אינם בסקופ הנוכחי. רשומים כאן כדי שלא יאבדו.
> פורמט: כל פיצ'ר עם תיאור קצר, מוטיבציה, רמת מורכבות, וקווי מימוש ראשוניים.

## 1. קול משני למחשבות (Thought voice)

**תיאור:** היום thoughts מוקראות באותו קול כמו ה-message. אופציה: קול שני, נמוך / לחישתי / מובחן, שמסמן קולית "זו מחשבה ולא תשובה".

**מוטיבציה:**
- בלי הפרדה קולית, קל לבלבל בין reasoning פנימי לתשובה אמיתית.
- מתאים לחלק מהמשתמשים — אחרים יעדיפו לא לשמוע thoughts בכלל.

**מורכבות:** קטנה (פרמטר ב-`tts.ts`, UI ב-config).

**קווי מימוש:**
- הוספת `?thoughtVoice=<voiceId>` ל-URL params.
- ב-config.html — dropdown נוסף + checkbox "השמע מחשבות".
- ב-server, `queueTts(text, "thought")` יעביר `voiceId` נפרד אם מוגדר.
- ConnState יקבל `thoughtVoiceId: string | null`.

**החלטה שהתקבלה:** **לא לעכשיו.** אותו voice בינתיים.

## 2. VAD + Gemini decision-maker

**תיאור:** במקום push-to-talk, להפעיל Voice Activity Detection (VAD) ש"שומע" את המשתמש כל הזמן. כש-VAD מזהה שהמשתמש מדבר, להעביר ל-Gemini את:
- מה שהמשתמש אמר (transcript זמני).
- מה שהמודל כותב כרגע.
- הקונטקסט של השיחה.

Gemini מחליט: **להפריע** (להתחיל prompt חדש) או **להמשיך** (להתעלם, זו רק רעש רקע / מילת מילוי).

**מוטיבציה:**
- שיחה ריאקטיבית אמיתית, בלי push-to-talk.
- מפתרון את "המשתמש מהמהם תוך כדי שהמודל מדבר" בלי לקטוע אותו לשווא.

**מורכבות:** גדולה.
- VAD בדפדפן (יש ספריות JS — Silero VAD בWASM).
- Logic של overlap בין recording רציף ל-STT chunks.
- Gemini call לכל זיהוי VAD.
- State machine מורכב מאוד.

**קווי מימוש:**
- ספריית VAD ב-frontend (silero-vad-web או דומה).
- streaming של chunks ל-backend בזמן אמת.
- backend עושה STT incremental + Gemini decision לכל סף.
- אם "להפריע" — `cancel` ל-ACP, ואז prompt חדש.

**החלטה שהתקבלה:** **לעתיד הרחוק.** דורש POC נפרד של VAD לפני.

**קווי מימוש:**

- סוכן עובד בworktree שלו, מקמט שם.
- כשמסיים — merge ל-master.
- חיסרון: צריך לסנכרן שינויי spec/walkthrough ידנית.

**החלטה שהתקבלה:** **רעיון לעתיד** — לנסות בסשן הבא אם יש עבודה מקבילית.

## 12. Full input streaming (model → ElevenLabs WS)

**תיאור:** במקום לחכות שהמודל יסיים סגמנט ואז לפתוח HTTP stream ל-ElevenLabs, להחזיק WebSocket פתוח ל-`wss://api.elevenlabs.io/.../stream-input` ולשלוח טקסט בזמן אמת ככל שהמודל כותב. ElevenLabs מזהה גבולות משפט בעצמה ומסנתז במקביל לכתיבת המודל.

**מוטיבציה:**
- חיסכון נוסף של ~0.8-1.2s לסגמנט מעבר ל-output streaming הקיים — מצטבר לחיסכון משמעותי לתשובות ארוכות.
- אבי הביע במפורש שזה הדבר שהיה רוצה: "איך שהמודל מתחיל לכתוב, ישר אנחנו מזרים ל-11 ומשמיעים".

**מורכבות:** גבוהה.

**קווי מימוש:**
- ניהול WS פתוח לכל segment (פתיחה, סגירה, error handling).
- תיאום בין stream של ACP (מהמודל) ל-WS ל-ElevenLabs ל-WS לדפדפן.
- דיווחים בקהילה על איכות prosody ירודה קצת בעברית עם v3 בstream-input — צריך לבדוק לפני אימוץ מלא.

**החלטה שהתקבלה:** **לא לעכשיו.** דורש POC נפרד למדידת איכות לעומת מורכבות. ה-HTTP streaming הקיים נותן רוב היתרון.

## 13. Per-segment WebSocket isolation (resilience)

**תיאור:** עוטף כל sgement TTS ב-WebSocket connection נפרד מול ElevenLabs, במקום HTTP stream על תהליך אחד. אם אילבן מתנהג מוזר על סגמנט (חוזר על עצמו, נתקע, פלט מעוות) — ניתן לזהות ולסגור רק אותו, בלי לאבד את שאר התור.

**מוטיבציה:**
- אבי דיווח שלפעמים אילבן "משתגע" באמצע סגמנט.
- היום אנחנו לא יכולים לבטל סגמנט ספציפי או לזהות אם סגמנט נכשל באמצע.

**מורכבות:** בינונית-גבוהה.

**קווי מימוש:**
- מעבר מ-HTTP stream ל-WebSocket לכל segment.
- timeout/health checks לכל סגמנט.
- אם נכשל — fallback ל-HTTP non-streaming או לסגמנט הבא.

**החלטה שהתקבלה:** **לא לעכשיו.** ההתנהגות "המשתגעת" של אילבן יחסית נדירה. נטפל אם תיהפך לבעיה תכופה.

## 15. TTS cache: LRU eviction + disk persistence

**תיאור:** ה-cache הנוכחי ב-`tts.ts` הוא `Map` בזיכרון ללא הגבלה ובלי שמירה לדיסק. בשיחות ארוכות זה צובר זיכרון, וכשמפעילים מחדש את השרת — הכל נמחק וצריך לעבור שוב את אילבן.

**מוטיבציה:**
- חיסכון משמעותי בעלות ובזמן בריצות חוזרות של אותם משפטים (במיוחד תוכן חוזר כמו "המשתמש שואל...").
- מניעת זיכרון בלתי-מוגבל בuptime ארוך.

**מורכבות:** קטנה-בינונית.

**קווי מימוש:**
- LRU map פשוט: capped at N entries (e.g. 500).
- שמירה לדיסק — תיקיית `.cache/tts/` עם מפתח hash → קובץ MP3.
- בעת startup, טעינה lazy: רק ה-cache hits בודקים אם הקובץ קיים בדיסק.
- TTL אופציונלי (חודש?).

**החלטה שהתקבלה:** **לא לעכשיו.** ה-cache בזיכרון מספיק ל-POC.

## 16a. צליל ייעודי למעבר ל-message (חשיבה → תשובה)

**תיאור:** היום יש צ'יים אחד שמושמע כשה-backend שולח event `thinking` (תחילת תור). הרעיון: להוסיף צליל **שני, מובחן**, שמושמע ברגע שהמודל עובר מ-thought chunks ל-message chunks — כלומר ה-chunk הראשון של תשובה אמיתית.

**מוטיבציה:**
- היום המשתמש שומע "חושב…" ולא יודע מתי בדיוק הסתיימה החשיבה. הוא מחכה לתחילת ה-TTS של המסר, אבל זה נמשך עוד שנייה כי TTS לוקח זמן.
- צליל מעבר ייתן feedback מיידי: "המודל סיים לחשוב, התשובה כבר נכתבת".

**מורכבות:** קטנה.

**קווי מימוש:**
- ב-backend, ב-`onChunk` (server.ts): track `lastKindEmitted`. כשמתחילים `message` ו-`lastKindEmitted !== "message"` — שלח event חדש `message_started`.
- ב-frontend, handler חדש: `playMessageStartChime()` — צליל קצר ומובחן.
- חשוב: לוודא שהצליל מושמע **פעם אחת לתור**, לא בכל מעבר thought↔message שיתכן בסטרימינג.

**החלטה שהתקבלה:** **לא לעכשיו.** רעיון טוב, נשאיר לאחר שהקולות הקיימים מיוצבים.

## 16b. טעינה אוטומטית של תיקייה ב-config.html

**תיאור:** היום ב-`config.html`, אחרי שמזינים cwd, צריך ללחוץ "טען אפשרויות" כדי לקבל models + sessions. שיפור: טעינה אוטומטית בשני מקרים:
1. אחרי בחירת תיקייה בפופאפ (אוטומטי, בלי כפתור).
2. בעת פתיחת הדף, אם יש cwd שמור ב-localStorage.

**מוטיבציה:**
- פחות לחיצות, חוויה זורמת יותר.
- ב-#2: המשתמש פותח config, רואה את התיקייה האחרונה כבר נטענת — מוכן לבחור session או model.

**מורכבות:** קטנה.

**קווי מימוש:**
- ב-`browse-btn`/`pickerSelectBtn` — אחרי `cwdInput.value = pickerCurrentPath` להפעיל את `loadBtn.click()` או ישירות את פונקציית הטעינה.
- בעת load של config.html — אם `stored.cwd` קיים, להפעיל auto-load.
- debounce על textbox typing — לטעון רק אחרי 1s של חוסר הקלדה (כדי לא לבזבז קריאות).

**שיקולים:**
- **בעד**: הרבה פחות לחיצות. UX מצוין.
- **נגד**: כל קריאה ל-`/api/info` spawnת opencode acp חדש (~3-5s). אם המשתמש בוחר תיקייה לטעות ומיד תיקייה אחרת — הוא ביזבז קריאה.

**החלטה שהתקבלה:** **לא לעכשיו.** רעיון טוב — נטמיע יחד עם עוד שיפורי UX של config.

## 16. Markdown TTS sanitization (defensive)

**תיאור:** ה-system prompt מבקש מהמודל לא להשתמש ב-markdown. אבל אם בכל זאת יחליק — היום ה-TTS מקריא את התווים literally ("כוכבית כוכבית bold כוכבית כוכבית"). פתרון: בdackend, לפני שליחה ל-TTS, להסיר markdown formatting מהטקסט.

**מוטיבציה:**
- היום: הצגה ב-HTML יפה (אחרי רינדור marked), אבל TTS מקבל את הטקסט הגולמי.
- אם המודל פולט `**bold**` או `# Title`, ההקראה תכלול גם את הסימנים.

**מורכבות:** קטנה.

**קווי מימוש:**
- פונקציה `stripMarkdown(text)` ב-`markdown.ts` שמסירה רק את formatting characters בלי להרוס את הטקסט.
- אופציות:
  - regex פשוט (`**, __, #, -, etc.`).
  - מעבר דרך marked עם renderer שמחזיר רק text.
- ב-`flushMessage`, להפעיל לפני `queueTts`.

**החלטה שהתקבלה:** **לא לעכשיו.** עדיין לא נצפו תקלות. אם יחליק — מימוש מהיר.
