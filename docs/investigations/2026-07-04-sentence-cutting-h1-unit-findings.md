# חקירת H1 (unit) — "ההקראה חותכת באמצע מילה": תווי-כיווניות וניקוד מול הסגמנטציה

## 1. הכרעה על H1 — **מאומת חלקית**

> **H1 (כפי שנוסחה):** "תווי כיווניות (RLM `U+200F`, LRM `U+200E`) וניקוד עברי משבשים את
> `Intl.Segmenter` ו/או את `TERMINATOR_RE` → חיתוך משפט/מילה במקום לא-צפוי."

**הכרעה:** H1 **מאומת כגורם-שיבוש אמיתי — אך אך ורק דרך זווית אחת: `TERMINATOR_RE`.**
שתי הזוויות האחרות (`Intl.Segmenter` sentence + word) **הופרכו**: הן עמידות ל-RLM/LRM/ניקוד.

| זווית | הכרעה | תמצית-ראיה |
| --- | --- | --- |
| **1. `TERMINATOR_RE` מול RLM אחרי המסיים** | ✅ **מאומת — זה הגורם** | `RLM` אינו whitespace → `[.!?]\s*$` נכשל → המשפט לא נפלט, נתקע כ-`remaining` |
| **2. `Intl.Segmenter` (sentence) סביב הגבול** | ❌ **מופרך** | RLM/LRM/ניקוד לפני/אחרי הנקודה **לא** מזיזים את גבול-המשפט |
| **3. `Intl.Segmenter` (word) `forceSplitWords`** | ❌ **מופרך** | RLM באמצע מילה נבלע לתוך אותו word-segment; החיתוך תמיד בגבול-מילה תקין |

**תיקון-תפיסה חשוב:** התסמין המדויק שנגרם מ-H1 **אינו** "חיתוך באמצע **מילה**" מילולי.
המנגנון המאומת הוא **החזקת-זנב (tail-holding)**: משפט שלם נתקע ולא נפלט בזמן, מה שגורם
ל-**פיגור-סגמנט**, ל-**flush גולמי בסוף-התור** (ברז 2), ול-**RLM מוביל שנדבק לתחילת הסגמנט הבא** —
כולם נשמעים למאזין כ"קול קטוע / חיתוך לא-טבעי", אך אף אחד מהם אינו שבירת-מילה בתוך `forceSplitWords`.
(ר' §3 לגבי מנגנון-חיתוך-מילה אפשרי אחר שלא נשלל.)

## 2. פירוט לכל אחת מ-3 הזוויות

### זווית 1 — `TERMINATOR_RE` מול RLM אחרי המסיים ✅ **הגורם**

ה-regex במקור (`sentence-boundary.ts:32`):
```ts
const TERMINATOR_RE = /[.!?]\s*$|\n\s*$/
```
משמש ב-`sentence-boundary.ts:68` להכרעה אם הסגמנט האחרון בבאפר של **פסקה-בודדת** "שלם"
(נפלט) או "חלקי" (נשמר כ-`remaining` עד ה-chunk הבא / ברז-2).

**ראיה ישירה (בדיקת ה-regex):**
```
TERMINATOR_RE.test("שלום עולם.")        = true      ← תקין
TERMINATOR_RE.test("שלום עולם." + RLM)  = false     ← הזווית החשודה — מאומת
TERMINATOR_RE.test("שלום עולם. " + RLM) = false      ← גם עם רווח לפני ה-RLM
TERMINATOR_RE.test("שלום עולם" + RLM + ".") = true   ← RLM לפני הנקודה לא מזיק
```
הסיבה: `U+200F` (RLM) **אינו** נכלל ב-`\s` של JS-regex. כשה-RLM יושב אחרי הנקודה,
בין ה-`.` לבין `$` יש תו שאינו-whitespace → `[.!?]\s*$` לא תופס.

**ראיה דרך הפונקציה המלאה (single-paragraph buffer):**
```
A1  "שלום עולם."          → sentences=["שלום עולם."]  remaining=""            ← נפלט
A2  "שלום עולם." + RLM    → sentences=[]               remaining="שלום עולם.‏"  ← נתקע!
A3  "שלום עולם. " + RLM   → sentences=[]               remaining="שלום עולם. ‏" ← נתקע!
```
codepoints של ה-remaining ב-A2 (מאשר שה-RLM צמוד אחרי הנקודה):
```
ש=U+05D9 … ם=U+05DD .=U+002E RLM=U+200F
```

**ההשפעה המערכתית (סימולציית-הצנרת `.tmp/h1-streaming-sim.ts`):**
`S2` — RLM אחרי כל נקודת-סיום, chunk-per-sentence:
```
chunk#0 +"…להיפלט.‏ "          → פלט:[]                          buffer="…להיפלט.‏ "
chunk#1 +"…כדי לצאת.‏ "         → פלט:["…להיפלט.‏"]  ← באיחור!    buffer="…כדי לצאת.‏ "
chunk#2 +"…מסיים את התור.‏"     → פלט:["…כדי לצאת.‏"] ← באיחור!    buffer="…מסיים את התור.‏"
[ברז2/turn-end] flush גולמי:  "…מסיים את התור.‏"                 ← המשפט האחרון נפלט רק בברז-2
```
→ **כל משפט נפלט באיחור של סגמנט אחד**, והמשפט האחרון נפלט רק ב-flush-הגולמי של ברז-2
(`speaker.svelte.ts:316`, ללא `splitIntoSentences`). זהו הפער בין ברז-1 לברז-2 שההקשר
כבר תיאר: המשפט מגיע ל-TTS מאוחר, ובסיטואציות-קצה (turn שלא מגיע ל-idle) — כלל לא בזמן.

`S3` — RLM בטוקן נפרד **אחרי** שהמשפט הראשון כבר נפלט:
```
chunk#4 +"להיפלט."   → פלט:["המשפט הראשון ארוך מספיק להיפלט."]  ← נקי (אין RLM עדיין)
chunk#5 +"‏ המשפט "   → פלט:[]  buffer="‏ המשפט "
…
chunk#9 +"הסוף."     → פלט:["‏ המשפט השני ממשיך עד הסוף."]  ← RLM מוביל דבוק!
```
→ תסמין-לוואי: `remaining.replace(/^\s+/, "")` (`sentence-boundary.ts:114`) מסיר רק
whitespace; **RLM שורד** ונדבק לתחילת הסגמנט הבא. הטקסט שנשלח ל-TTS פותח ב-`U+200F` —
מקור אפשרי נוסף להגייה/קטיעה חריגה בתחילת סגמנט.

**אי-תלות בספק (מחזק את H1):** הגורם הוא **תוכן הטקסט** (המודל פולט RLM בעברית), לא timing.
לכן הוא מסביר את התופעה גם ב-claude וגם ב-opencode ללא תלות ב-tail של ספק מסוים — בדיוק
כפי שנצפה חי ב-2026-06-27.

### זווית 2 — `Intl.Segmenter` granularity `"sentence"` ❌ **מופרך**

RLM/LRM/ניקוד **לא** מזיזים את גבול-המשפט. השוואת זהות עם/בלי תווים:
```
B1  RLM בתחילת המשפט:  "‏המשפט…כיווניות. המשפט השני."
    → ["‏המשפט…כיווניות.", "המשפט השני."]   ← 2 משפטים, פיצול תקין
B2  בקרה בלי RLM:      → ["המשפט…כיווניות.", "המשפט השני."]   ← זהה
B3  ניקוד מלא לפני הנקודה: "שְלָוֹם עָולָם. …"  → פוצל תקין
B4  דו-לשוני עם LRM+RLM:  "…‎npm run build‏ והיא עובדת. …"  → 2 משפטים, פיצול תקין
```
ה-Segmenter של ICU מתעלם מתווי-הכיווניות והניקוד לצורך זיהוי גבול-משפט. אין כאן שיבוש.

### זווית 3 — `Intl.Segmenter` granularity `"word"` (`forceSplitWords`) ❌ **מופרך**

RLM באמצע מילה **נבלע** לתוך אותו word-segment — המילה לא נשברת:
```
word-seg על  "המ" + RLM + "משפט":
  → "המ‏משפט"   isWordLike=true   [ה מ RLM מ ש פ ט]   ← מילה אחת! לא פוצל
```
ובמשפט ארוך (>200) עם RLM אחרי כל רווח (C2), החיתוך-בכוח נופל תמיד **בין** מילים:
```
… "שתשמור ‏על"  |  "‏שלמות ‏המילים …"    ← גבול-מילה תקין, לא אמצע-מילה
```
→ `forceSplitWords` עמיד ל-RLM. **הוא לא הגורם לחיתוך-אמצע-מילה.**

**תסמין-לוואי מדיד (לא שבירת-מילה, אבל כדאי לדעת):** RLM **מנפחים את ספירת-האורך**.
אותו משפט: 224 תווים נקי מול **264** תווים עם RLM אחרי כל רווח. מאחר ש-`maxChars=200`
נבדק על המחרוזת כולל תווי-הכיווניות (`sentence-boundary.ts:103,125`), `forceSplitWords`
**מתפעל מוקדם/תדיר יותר** ממה שהמאזין מצפה לפי מספר-המילים הנשמע → יותר חיתוכים
(עדיין בגבול-מילה, אך צפופים יותר).

## 3. מנגנונים אחרים (לא-H1) שנצפו / לא-נשללו

1. **flush גולמי בברז-2 ללא `splitIntoSentences`** (`speaker.svelte.ts:302-320`). זה
   *מגביר* את נזק זווית-1 (המשפט התקוע נפלט גולמי בסוף-תור), אך הוא גם וקטור עצמאי:
   כל טקסט שנשאר ב-`state.buffer` בסוף-תור נשלח כסגמנט **בלי סגמנטציה נוספת** — אם הבאפר
   מכיל כמה משפטים/שארית-ארוכה, הם יוצאים כגוש אחד לא-מפוצל.
2. **חיתוך-אמצע-מילה מילולי לא שוחזר ב-unit כלל.** נקודת-החיתוך היחידה (`forceSplitWords`)
   מוכחת עמידה (זווית 3) + מכוסה בטסט קיים (`sentence-boundary.test.ts` test 6). אם
   "אמצע מילה" נצפה חי, ייתכן שהוא (א) תפיסה סובייקטיבית של הפיגור/flush מזווית-1, או
   (ב) שורש נפרד **מחוץ ל-core** — למשל חלוקת ה-chunks של ה-TTS ל-audio-segments בצד
   ה-Player/AudioStream, או התנהגות ה-Gemini-PCM. **דורש נתונים חיים (`WIRE_RECORD` + cache)
   כדי לשלול/לאשר** — מעבר ל-scope של חקירת-unit זו.

## 4. המלצת כיוון-תיקון (לא יושם)

### מומלץ — נרמול תווי-כיווניות **בכניסת הסגמנטציה** (נקודת-שינוי יחידה)

**נקודת-קוד מדויקת:** `packages/core/src/voice/sentence-boundary.ts`, בתוך
`splitIntoSentences`, מיד אחרי `if (buffer.length === 0) return …` (שורה 39), לפני יצירת
ה-`Intl.Segmenter`:
```ts
// TTS-only: תווי-כיווניות נחוצים לתצוגה (הבועות מרונדרות מ-segments המקוריים),
// אך משבשים את TERMINATOR_RE ומנפחים את ספירת-maxChars. הסרתם כאן בטוחה —
// הטקסט הזה זורם רק ל-TTS, לא לתצוגה.
buffer = buffer.replace(/[‎‏‪-‮⁦-⁩]/g, "")
```
(מכסה RLM/LRM + embeddings `U+202A-U+202E` + isolates `U+2066-U+2069`.)

**למה זו הבחירה הנכונה:**
- פותרת את **זווית-1** (ה-terminator שוב תופס), את ה-**RLM-המוביל** (S3), ואת **ניפוח-האורך**
  של `forceSplitWords` — כולן במכה אחת.
- **נקודת-שינוי יחידה** ב-core, נבדקת unit. ה-`remaining` שחוזר כבר מנורמל → הבאפר
  ב-`speaker` (`state.buffer = remaining`) נשאר נקי, וגם ה-flush-הגולמי של ברז-2 יורש טקסט נקי.
- **אינה פוגעת בתצוגה**: ההנחיה הגלובלית דורשת RLM ב-**תצוגה** של הבועות; אלה מרונדרות
  מ-`bubble.segments` המקוריים, לא מהטקסט שעובר ל-TTS. מסלול-ה-TTS אינו זקוק ל-RLM.
- **שמרנות:** *לא* להסיר ניקוד (`U+0591-U+05C7`) — זווית-2/3 מוכיחות שהוא לא מזיק, והוא
  עשוי לשפר הגייה ב-TTS. לנרמל אך ורק תווי-כיווניות (bidi controls).

### חלופות (נחותות)
- **תיקון `TERMINATOR_RE` בלבד** ל-`/[.!?][\s‎‏]*$|\n[\s‎‏]*$/`: ממוקד
  אך **חלקי** — פותר זווית-1 בלבד, לא את ה-RLM-המוביל ולא את ניפוח-האורך.
- **הרצת `splitIntoSentences` גם בברז-2** (`speaker.svelte.ts:316`): שיפור-איכות עצמאי מומלץ
  *בנוסף* (מכסה את המנגנון §3.1), אך אינו מטפל בשורש-ה-RLM.

**המלצה משולבת ל-brief:** נרמול-bidi בכניסת `splitIntoSentences` (עיקר) **+** להישקל: הרצת
split גם בברז-2 של `speaker`.

## 5. מקרי-בדיקה לטסטי-רגרסיה (ל-brief-הביצוע)

לשילוב ב-`packages/core/tests/voice/sentence-boundary.test.ts` (vitest קיים). לבנות תווים
ב-JS (לא ליטרלים): `const RLM = "‏"`, `const LRM = "‎"`.

1. **RLM אחרי מסיים נפלט (הליבה):**
   `splitIntoSentences("משפט ראשון ארוך מספיק להיפלט." + RLM)` →
   ציפייה-לאחר-תיקון: `sentences=["משפט ראשון ארוך מספיק להיפלט."]`, `remaining=""`
   (היום: `sentences=[]`, `remaining="…להיפלט.‏"`).
2. **RLM + רווח אחרי מסיים:** `"…להיפלט." + RLM + " "` → נפלט, `remaining=""`.
3. **בקרה — בלי RLM:** `"…להיפלט."` → נפלט (מוודא אי-רגרסיה על הנתיב הנקי).
4. **RLM לא נדבק לתחילת הסגמנט הבא (S3):** streaming עם RLM בתחילת chunk המשך →
   הסגמנט הנפלט **לא** מתחיל ב-`U+200F` (`expect(seg.startsWith("‏")).toBe(false)`).
5. **ניקוד אינו מזיק (הגנה על זווית-2):** `"שְלָוֹם עָולָם. משפט שני ארוך מספיק כאן."` →
   2 משפטים, פיצול תקין (לוודא שהתיקון לא נגע בניקוד).
6. **ניפוח-אורך: משפט >200 עם RLM אחרי כל רווח** → מס' הסגמנטים לאחר-תיקון = כמו הגרסה
   הנקייה (RLM לא מוסיפים חיתוכים), וכל סגמנט ≤ 200 ומסתיים בגבול-מילה.
7. **דו-לשוני עם LRM/RLM:** `"…‎npm run build‏ עובד. משפט הבא כאן."` → פיצול תקין, בלי
   תווי-כיווניות בטקסט הנפלט.

## סיכום (5-8 שורות)

**H1 מאומת חלקית.** הגורם האמיתי הוא **זווית 1 בלבד — `TERMINATOR_RE`**: תו RLM (`U+200F`)
אחרי סימן-הסיום אינו-whitespace, לכן `[.!?]\s*$` נכשל, המשפט לא נפלט ונתקע כ-`remaining` →
**פיגור-סגמנט + flush גולמי בברז-2 + RLM שנדבק לתחילת הסגמנט הבא**. זוויות 2 ו-3
(`Intl.Segmenter` sentence/word) **הופרכו** — עמידות ל-RLM/LRM/ניקוד; `forceSplitWords`
לא שובר מילה. **חיתוך-אמצע-מילה מילולי לא שוחזר ב-unit** — התסמין הנשמע נובע מהחזקת-הזנב,
או משורש נפרד מחוץ ל-core (Player/PCM) שדורש נתונים חיים. **תיקון מומלץ:** נרמול תווי-כיווניות
(`/[‎‏‪-‮⁦-⁩]/g`) בכניסת `splitIntoSentences` ב-`sentence-boundary.ts:39`
— נקודת-שינוי יחידה בטוחה שאינה פוגעת בתצוגה (הבועות מרונדרות מ-segments המקוריים), פותרת
את שלושת התסמינים בבת-אחת. אין לגעת בניקוד.
